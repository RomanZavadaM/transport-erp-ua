# Огляд архітектури

## Базовий принцип
TransportERP-UA проєктується від найпростішої практичної інсталяції вгору.

Базовий локальний сценарій — **встановлюваний desktop-застосунок** на одному комп’ютері з SQLite та локальними файлами. Центральний рівень є опційним вищим рівнем, а не умовою роботи локального АТП.

## Локальний вузол

Мінімальний локальний склад:

- desktop application shell;
- локальний backend;
- SQLite як оперативна БД;
- локальне файлове сховище;
- вбудований backup/restore;
- механізм підготовки та підтвердженої передачі даних на вищий рівень.

Користувач запускає TransportERP-UA як звичайну програму. Відкривати `localhost` у браузері, налаштовувати PostgreSQL, Docker, Redis або S3 для локальної роботи не потрібно.

Внутрішньо UI може бути реалізований на React/Next.js і показуватися в desktop WebView/shell; це не змінює користувацьку модель застосунку.

## Центральний рівень

За потреби вищий рівень може використовувати:

- FastAPI services;
- PostgreSQL;
- серверне файлове/object storage;
- централізовану звітність та адміністрування.

Передача даних з локального вузла виконується лише після підтвердження локального оператора. Після central ACK передані дані локально стають read-only і змінюються на центральному рівні.

## Основний доменний потік

`Schedule → Trip → Duty → призначення ресурсів → перевірки → Release → Waybill → фактичне виконання → закриття → звітність`.

`Trip` і `Duty` навмисно розділені: один наряд може містити кілька рейсів.

## Цілісність

- критичні бізнес-правила перевіряє backend;
- SQLite використовує транзакції, FK, UNIQUE, CHECK, indexes/triggers де доречно;
- PostgreSQL на центральному рівні може додатково використовувати RLS, exclusion constraints, row locks та інші defense-in-depth механізми;
- закрита історія версіонується;
- Plan і Fact зберігаються окремо;
- frontend/desktop shell не приймає остаточних бізнес-рішень самостійно.

## Практичне масштабування

Одна кодова база підтримує:

1. один комп’ютер без центрального сервера;
2. локальний вузол + центральний рівень;
3. кілька локальних вузлів, що передають схвалені дані на спільний центральний рівень.

Не створюється окрема `Lite` версія продукту.
