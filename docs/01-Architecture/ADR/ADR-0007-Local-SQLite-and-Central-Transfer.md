# ADR-0007 — Локальна SQLite та передача даних на вищий рівень

## Статус
Прийнято для architecture-v1.6.

## Контекст
TransportERP-UA повинен однаково практично працювати в малому АТП на одному комп’ютері та в підприємстві з вищим центральним рівнем. Локальна робота не повинна залежати від PostgreSQL, Docker, Redis, S3 або постійного доступу до центрального сервера.

## Рішення

### 1. Локальний вузол
Кожний локальний вузол TransportERP-UA працює на SQLite як на своїй оперативній БД.

Мінімальна інсталяція може складатися з одного комп’ютера:

- TransportERP-UA;
- FastAPI backend;
- SQLite;
- локальне файлове сховище документів;
- локальний backup;
- браузер на цьому ж комп’ютері або робочі місця в LAN через API.

PostgreSQL, Redis, S3-compatible storage, Docker та окремий worker не є обов’язковими для локального вузла.

### 2. Джерело істини
Поки конкретні дані не передані на вищий рівень і передача не підтверджена центральним рівнем, джерелом істини є локальна SQLite.

Після успішної передачі та отримання ACK:

- передані дані вважаються керованими центральним рівнем;
- локальна копія цих даних стає read-only;
- локальний backend повинен блокувати UPDATE/DELETE таких даних, а не покладатися лише на UI;
- подальша модифікація переданих даних виконується на центральному рівні;
- оновлена центральна версія може повертатися на локальний вузол як read-only copy.

### 3. Хто ініціює передачу
Передача може бути підготовлена:

- локальним оператором добровільно;
- запитом з вищого рівня;
- правилом/розкладом, налаштованим підприємством.

Але фактична передача **завжди потребує явного підтвердження локального оператора**.

Запит зверху або правило лише формують pending request / candidate batch. Автоматичного вилучення даних з локального вузла без локального підтвердження немає.

### 4. Коли блокується локальне редагування
Локальне редагування блокується тільки після підтвердженої успішної передачі.

Невдала, перервана або непідтверджена передача не змінює локальне ownership і не блокує роботу.

### 5. Технічний стан передачі
Мінімальний технічний стан для запису або transfer unit:

- `LOCAL` — локально authoritative, редагування дозволено;
- `PENDING_APPROVAL` — підготовлено локально, за запитом зверху або правилом;
- `TRANSFERRING` — підтверджена оператором передача виконується;
- `CENTRAL` — центральний ACK отримано, локальна копія read-only.

Для практичного відновлення/діагностики зберігаються щонайменше:

- `origin_node_id`;
- `transfer_batch_id`;
- `approved_by`;
- `approved_at`;
- `transferred_at`;
- `central_ack_id` або еквівалентний receipt;
- version/checksum для перевірки цілісності.

### 6. Передача виконується пакетно
Користувач працює не з технічними таблицями, а з зрозумілим пакетом/вибіркою даних. Backend сам включає потрібні залежні записи так, щоб у центр не потрапляв логічно неповний набір.

### 7. Outbox
Outbox використовується як надійна технічна черга доставки вже схваленої передачі та інших асинхронних дій. Outbox не визначає право володіння даними.

Право змінюється лише після central ACK.

### 8. Центральний рівень
Центральний рівень може використовувати PostgreSQL для консолідації, централізованого редагування переданих даних, звітності та вищого управління.

Відсутність центрального рівня не обмежує повноцінну локальну роботу малого АТП.

### 9. Файли
Локально файли можуть зберігатися у звичайному каталозі під керуванням TransportERP-UA. S3-compatible storage є опцією центрального/серверного рівня, а не локальною вимогою.

### 10. Backup
Локальний вузол повинен мати вбудований практичний backup SQLite + документів у вибраний користувачем каталог/зовнішній диск/NAS. Копія на тому самому фізичному диску не вважається достатнім backup.

## Наслідки

- SQLite стає базовою operational БД локального вузла.
- PostgreSQL перестає бути обов’язковою залежністю локальної інсталяції.
- RLS та PostgreSQL-specific constraints застосовуються лише там, де використовується PostgreSQL, насамперед на центральному рівні.
- Критичні бізнес-правила повинні бути реалізовані в backend і підтримані доступними локальними SQLite constraints/triggers; PostgreSQL може додавати сильніші defense-in-depth constraints.
- M1.5 має початися зі SQLite/local-node foundation, audit та практичного механізму підтвердженої передачі, а не з PostgreSQL-only worker infrastructure.
