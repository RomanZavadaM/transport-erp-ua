# ADR-0007 — Локальний застосунок, SQLite та передача даних на вищий рівень

## Статус
Прийнято для architecture-v1.6.

## Контекст
TransportERP-UA повинен практично працювати як у малому АТП на одному комп’ютері, так і в підприємстві з вищим центральним рівнем. Локальна робота не повинна залежати від PostgreSQL, Docker, Redis, S3, постійного Internet або відкритої вкладки браузера.

## Рішення

### 1. Локальний рівень — встановлюваний застосунок
Локальний TransportERP-UA є звичайним застосунком, який користувач запускає з ярлика/меню ОС.

Користувач не повинен вручну:

- запускати сервер;
- відкривати `localhost` у браузері;
- налаштовувати PostgreSQL;
- працювати з Docker;
- знати порти або службові процеси.

Внутрішньо застосунок може використовувати локальний API та WebView/desktop shell, але це технічна деталь. Робоче середовище користувача — одне вікно TransportERP-UA.

Мінімальна локальна інсталяція:

- desktop application shell;
- локальний backend;
- SQLite;
- локальне файлове сховище документів;
- локальний service/worker лише якщо він реально потрібен і запускається самим застосунком;
- вбудований backup/restore.

Віддалене відкриття через браузер або LAN може бути додатковою можливістю, але не є базовою моделлю локальної роботи.

### 2. Локальна оперативна БД
Кожний локальний вузол TransportERP-UA працює на SQLite як на своїй оперативній БД.

PostgreSQL, Redis, S3-compatible storage, Docker та окремий сервер не є обов’язковими залежностями локального вузла.

### 3. Джерело істини
Для конкретних даних існує лише два business-authority стани:

- `LOCAL` — джерелом істини є локальна SQLite, локальне редагування дозволено;
- `CENTRAL` — дані успішно передані й підтверджені central ACK, подальше редагування виконується на центральному рівні, локальна копія read-only.

**До отримання valid central ACK authority залишається `LOCAL`.**

`PENDING_APPROVAL`, `TRANSFERRING`, `FAILED` тощо — це статус передачі, а не зміна джерела істини.

### 4. Хто ініціює передачу
Передача може бути підготовлена:

- локальним оператором добровільно;
- запитом з вищого рівня;
- правилом/розкладом, налаштованим підприємством.

Фактична передача **завжди потребує явного підтвердження локального оператора**.

Запит зверху або правило лише формують pending request / candidate batch. Автоматичного вилучення даних з локального вузла без локального підтвердження немає.

### 5. Статуси transfer batch
Мінімально:

- `PENDING_APPROVAL` — пакет підготовлено, але оператор ще не підтвердив;
- `TRANSFERRING` — оператор підтвердив, пакет передається/може повторюватися після технічної помилки;
- `FAILED` — остання спроба неуспішна, authority все ще `LOCAL`;
- `ACKNOWLEDGED` — central прийняв пакет і повернув valid ACK;
- `CANCELLED` — pending/failed package скасований локально, якщо transfer contract це дозволяє.

Поки batch не `ACKNOWLEDGED`, data authority залишається `LOCAL`.

### 6. Що відбувається під час передачі
Після local approval payload пакета фіксується версіями/checksum.

Поки batch `TRANSFERRING`, включені records тимчасово блокуються від звичайного редагування, щоб approved payload не змінився в дорозі.

Це **transfer lock**, а не передача authority.

Якщо оператор скасував допустимий failed transfer або пакет повернуто у стан для переформування, transfer lock знімається і local editing знову дозволено.

### 7. Коли локальні дані стають read-only
Тільки після:

1. central успішно прийняв batch;
2. central повернув valid receipt/ACK;
3. local application перевірив ACK;
4. local transaction записав authority=`CENTRAL`.

Після цього local backend блокує UPDATE/DELETE незалежно від UI.

### 8. Передача виконується зрозумілими пакетами
Оператор не працює з технічними таблицями. UI показує зрозумілий пакет даних, який буде передано. Backend сам додає потрібні залежності та перевіряє, що набір не є логічно неповним.

### 9. Outbox / delivery queue
Outbox використовується лише як надійна технічна черга доставки вже схваленої передачі та інших конкретних async-задач.

Outbox не визначає authority. Authority змінюється лише після central ACK.

### 10. Центральний рівень
Центральний рівень може використовувати PostgreSQL для:

- приймання переданих даних;
- централізованого редагування вже переданих даних;
- консолідованої звітності;
- вищого управління.

Відсутність центрального рівня не обмежує повноцінну локальну роботу малого АТП.

### 11. Файли
Локально файли зберігаються у керованому застосунком каталозі. S3-compatible storage є опцією центрального/серверного рівня, а не локальною вимогою.

### 12. Backup
Локальний застосунок має вбудований backup/restore SQLite + документів у вибраний користувачем каталог, зовнішній диск або NAS.

Копія на тому самому фізичному диску може бути швидкою локальною копією, але не вважається достатнім захистом від втрати комп’ютера/диска.

## Практичні наслідки

- перша production-конфігурація може бути одним Windows/Linux/macOS комп’ютером;
- локальна інсталяція не потребує DBA або системного адміністратора;
- SQLite стає базовою operational БД локального вузла;
- PostgreSQL перестає бути обов’язковою залежністю локального застосунку;
- PostgreSQL-specific RLS/constraints застосовуються на центральному рівні, де PostgreSQL реально використовується;
- критичні бізнес-правила реалізуються в backend та підсилюються доступними SQLite constraints/triggers;
- desktop packaging, запуск backend, оновлення, backup і recovery є частиною продукту, а не інструкцією для користувача;
- M1.5 починається зі SQLite/local-node foundation, audit і механізму підтвердженої передачі, а не з PostgreSQL-only worker infrastructure.
