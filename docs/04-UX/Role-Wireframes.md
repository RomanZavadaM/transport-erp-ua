## 6. Repair Workspace

```text
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│ Repair RO-2026-0041     ВС7777АА      IN_PROGRESS      Blocks operation: YES           │
├───────────────────────────────┬─────────────────────────────────────────────────────────┤
│ Опис / diagnosis             │ Timeline / state                                        │
│ ...                           │ OPEN → DIAGNOSIS → APPROVED → IN_PROGRESS               │
│                               │                                                         │
│ Роботи / parts               │ Related defects                                          │
│ ...                           │ DEF-...                                                  │
├───────────────────────────────┴─────────────────────────────────────────────────────────┤
│ [Waiting parts] [Complete repair]                                                       │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

State actions залежать від repair state machine.

## 7. Common role handoff visibility

Кожен workspace показує, що чекає саме від цієї ролі:

- Mechanic queue — `technical check required`;
- Medic queue — `medical check required`;
- Dispatcher board — `waiting for mechanic/medic`;
- Manager dashboard — aggregated blocking count.

Не використовувати один generic `PENDING` без контексту.

## 8. Acceptance criteria

- кожна людська роль має визначений landing workspace;
- primary daily task не потребує переходу в unrelated admin/master-data section;
- queues чітко показують наступну дію;
- completed checks read-only;
- driver workspace не відкриває чужі дані;
- admin workspace не містить business override;
- handoff між ролями відображається серверним state, а не ручними повідомленнями.
