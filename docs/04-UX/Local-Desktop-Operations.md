# Local Desktop — службові робочі екрани

Статус: **architecture-v1.6 / M1.5 UX baseline**

Мета — дати нормальний користувацький UX для локального desktop-застосунку. Оператор не повинен бачити `outbox`, SQL, порти, UUID batches як основний інтерфейс.

## 1. Головне меню локального застосунку

Окрім бізнес-модулів, локальний TransportERP-UA має три службові пункти:

- **Передача даних**;
- **Резервні копії**;
- **Стан системи**.

Вони доступні за permission, але не заховані в технічному developer menu.

## 2. Передача даних — список

Екран показує окремими групами:

### Очікують підтвердження

- хто/що підготував: `Вручну`, `Запит з центру`, `Правило`;
- короткий опис пакета;
- кількість об’єктів;
- дата/час підготовки;
- кнопки `Переглянути`, `Підтвердити передачу`, `Відхилити`.

### Передаються / помилка

- дата підтвердження;
- хто підтвердив;
- статус;
- остання спроба;
- зрозуміла помилка;
- `Повторити` там, де це безпечно;
- `Скасувати передачу` лише якщо workflow дозволяє і central ще не підтвердив прийняття.

### Передані

- дата передачі;
- central receipt/номер підтвердження у technical details;
- хто підтвердив локально;
- кількість об’єктів;
- можливість відкрити перелік read-only records.

## 3. Картка пакета передачі

Перед натисканням `Підтвердити передачу` оператор бачить:

- що саме передається людськими назвами;
- період/дати;
- кількість документів/записів;
- причину підготовки;
- чи є запит зверху;
- які записи після ACK стануть недоступними для локального редагування.

Критичне підтвердження:

> Після успішного прийняття центральним рівнем ці дані будуть доступні локально тільки для перегляду. Подальші зміни виконуються на центральному рівні.

Не показувати технічний JSON як основний preview.

## 4. Запит зверху

Central request показується як вхідний запит:

- хто/який central вузол запросив;
- дата запиту;
- що просить передати;
- причина/коментар, якщо є;
- `Підготувати пакет` / `Відхилити`.

Навіть після автоматичної підготовки пакет лишається в `Очікують підтвердження`.

Немає кнопки/механізму, який дозволяє central автоматично натиснути local approval.

## 5. Правило передачі

Правило може, наприклад, підготувати кандидати за умовою/розкладом.

У UX правило означає:

- система автоматично сформувала pending package;
- оператор отримав ненав’язливий індикатор;
- оператор відкриває пакет і підтверджує або відхиляє.

Не використовувати wording `Автоматично передано`, якщо local operator не підтверджував передачу.

## 6. Read-only після central ACK

На картках переданих об’єктів показується помітний, але не агресивний banner:

**Керується центральним рівнем — локальне редагування недоступне.**

Доступні:

- перегляд;
- друк/експорт, якщо permission дозволяє;
- audit/history;
- інформація про передачу;
- актуалізація central version через system sync.

Недоступні звичайні `Редагувати`, `Видалити`, `Змінити статус` local actions.

Backend все одно перевіряє authority незалежно від disabled buttons.

## 7. Temporary transfer lock

Після local approval і до ACK record authority все ще `LOCAL`, але approved payload не можна змінювати.

UI показує:

**Передача триває — редагування тимчасово призупинено.**

Якщо failed transfer дозволено скасувати й lock знято, звичайне редагування повертається.

Не показувати цей стан як `Керується центром`, бо central authority ще не настала.

## 8. Резервні копії

Екран показує:

- останню успішну копію;
- destination;
- розмір;
- статус;
- `Створити резервну копію зараз`;
- `Змінити місце збереження`;
- простий розклад;
- `Відновити з резервної копії` у контрольованому recovery flow.

Warnings:

- destination unavailable;
- backup overdue;
- backup failed;
- backup зберігається тільки на тому самому physical disk.

Не показувати користувачу `sqlite3 .backup` або SQL-команди.

## 9. Відновлення

Restore wizard:

1. вибір backup package;
2. показ дати/версії/node;
3. перевірка checksum;
4. попередження про заміну поточного local state;
5. safety backup current state;
6. restore;
7. integrity check;
8. результат.

При помилці не залишати користувача з blank window — показати recovery status та diagnostic export.

## 10. Стан системи

Один компактний екран:

### Застосунок
- version/build;
- node id;
- schema version.

### Дані
- SQLite: `Нормально / Помилка`;
- DB size;
- documents size;
- free disk space.

### Backup
- last successful backup;
- destination;
- warning if overdue.

### Central
- `Не налаштовано / Доступний / Недоступний`;
- pending approval count;
- active/failed transfer count.

### Integrity
- last check;
- open warnings/errors;
- `Перевірити систему`.

Кнопки:

- `Відкрити журнал`;
- `Створити діагностичний пакет`;
- `Перевірити систему`.

## 11. Startup failure UX

Якщо backend/SQLite не стартував, desktop shell не показує порожнє WebView.

Показується recovery screen з:

- короткою причиною;
- application/data path;
- `Повторити запуск`;
- `Відкрити журнал`;
- `Відновити з резервної копії` там, де доречно;
- `Створити діагностичний пакет`.

## 12. Offline UX

Відсутність central/Internet не повинна виглядати як аварія всього застосунку.

Якщо local DB справна:

- business work continues;
- central indicator може бути сірим/жовтим;
- transfer pending/failed status видно окремо;
- немає full-screen `Система недоступна` тільки через central outage.

## 13. Заборонені UX-антипатерни

Не робити в Local Desktop:

- браузерну вкладку як основний launcher;
- сирий outbox table для оператора;
- технічні UUID замість назв/номерів;
- автоматичне local approval;
- silent authority change;
- editable form для authority=`CENTRAL` із помилкою лише після Save;
- backup лише через командний рядок;
- popup, що зникає і є єдиним повідомленням про failed backup/transfer.

## 14. M1.5 UX acceptance

Під час ручного тесту користувач без знань SQL/серверів повинен уміти:

1. запустити TransportERP-UA з ярлика;
2. побачити pending central request;
3. переглянути пакет;
4. самостійно підтвердити передачу;
5. зрозуміти interrupted transfer;
6. повторити її;
7. після ACK побачити, що record read-only і чому;
8. створити backup;
9. побачити стан системи;
10. отримати diagnostic package при проблемі.
